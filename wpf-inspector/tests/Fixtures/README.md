# Owned WPF fixture

The fixture is a test target and does not reference the inspector. From the repository root, run `scripts/publish_fixtures.ps1` to publish all six framework/architecture cells and build the OwnedAttach harness with locked restores, without launching them. The desktop workflow runs this after building the inspector payload. Use the SDK and runtime restrictions in the implementation brief. `smoke.ps1` launches these paths, probes UI Automation, prints executable SHA-256 hashes, and terminates only the processes it starts. It is a diagnostic, not a matrix acceptance report. Runtime roots in that script describe this machine and may need adjustment.

The current-user-only named pipe `WinTestKit.Fixture.<pid>` accepts newline-delimited UTF-8 JSON and returns one JSON line. Commands: `{"cmd":"counters"}`, `{"cmd":"reset"}`, `{"cmd":"gcCollect"}`, `{"cmd":"exit"}`, and `{"cmd":"scenario","name":"...","value":0}`. Scenarios include `openPopup`, `changeDataContext`, `scrollRows`, `openSecondWindow`, `closeWindow` (the second window), `addDynamic`, and `clearDynamic`. Counters and control operations are for test setup only; this channel does not expose inspected values. `--hash-report <path>` records hashes at startup before inspection.

For adverse tests, start a separate owned process. `setSlowDelay` sets the `Slow` getter delay in milliseconds (clamped to 0..60000). `resetHang` arms the shared wait; reading `Hanging` then blocks that dispatcher until `releaseHang`. `blockDispatcher` queues the same wait directly on the main dispatcher; `dispatcher.blocked` and `dispatcher.released` counters show entry and release. The pipe remains on a background thread, so `releaseHang` remains available while the UI is blocked. Start the second dispatcher before blocking and wait until its window exists. A scenario response acknowledges queuing, not completion: poll counters or UIA. Release before normal exit; if necessary terminate only the owned process. These controls do not cancel a getter and do not establish inspector timeout or isolation behavior.


## Owned WinForms fixture

`WinFormsFixture` is the WinForms counterpart: `WinTestKit.WinFormsFixture.exe`, published to `WinFormsFixture/bin/cells/<tfm>-<arch>` for the same six framework/architecture cells by `scripts/publish_fixtures.ps1`. It does not reference the inspector. Its form `mainForm` ("WinForms Fixture") has `button1` ("OK"), `button2`, `textBox1`, a password box `passwordBox`, `label1`, `checkBox1`, `comboBox1`, `listBox1`, `groupBox1` with two nested buttons, `tabControl1` with two pages, `dataGridView1`, `menuStrip1` with File and Help items, and `fixtureUserControl1` (`FixtureUserControl`): public, private and internal properties and fields, a `[DefaultValue]` property, a property whose getter throws, and the methods `RecordWrite(string value, int number)` (shown in its label), `Add`, `Echo`, `Toggle` and `Reset`.

The current-user-only named pipe `WinTestKit.WinFormsFixture.<pid>` takes newline-delimited JSON: `{"cmd":"counters"}` returns `writeCount`, `{"cmd":"exit"}` closes the form and `{"cmd":"scenario","name":"openSecondForm|openDuplicateButtons|closeForm"}` opens or closes windows (`--scenario <name>` runs one at startup). `openDuplicateButtons` opens unnamed buttons with the same text, so their labels differ by position only.
