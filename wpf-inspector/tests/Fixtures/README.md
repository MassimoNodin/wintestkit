# Owned WPF fixture

The fixture is a test target and does not reference the inspector. Publish each framework with `dotnet publish WpfFixture/WpfFixture.csproj -c Release -f <tfm> -r win-<x86|x64> --self-contained false -p:PlatformTarget=<x86|x64> -o WpfFixture/bin/cells/<tfm>-<arch>`. Use the SDK and runtime restrictions in the implementation brief. `smoke.ps1` launches these paths, probes UI Automation, prints executable SHA-256 hashes, and terminates only the processes it starts. It is a diagnostic, not a matrix acceptance report. Runtime roots in that script describe this machine and may need adjustment.

The current-user-only named pipe `WinTestKit.Fixture.<pid>` accepts newline-delimited UTF-8 JSON and returns one JSON line. Commands: `{"cmd":"counters"}`, `{"cmd":"reset"}`, `{"cmd":"gcCollect"}`, `{"cmd":"exit"}`, and `{"cmd":"scenario","name":"...","value":0}`. Scenarios include `openPopup`, `changeDataContext`, `scrollRows`, `openSecondWindow`, `closeWindow` (the second window), `addDynamic`, and `clearDynamic`. Counters and control operations are for test setup only; this channel does not expose inspected values. `--hash-report <path>` records hashes at startup before inspection.

For adverse tests, start a separate owned process. `setSlowDelay` sets the `Slow` getter delay in milliseconds (clamped to 0..60000). `resetHang` arms the shared wait; reading `Hanging` then blocks that dispatcher until `releaseHang`. `blockDispatcher` queues the same wait directly on the main dispatcher; `dispatcher.blocked` and `dispatcher.released` counters show entry and release. The pipe remains on a background thread, so `releaseHang` remains available while the UI is blocked. Start the second dispatcher before blocking and wait until its window exists. A scenario response acknowledges queuing, not completion: poll counters or UIA. Release before normal exit; if necessary terminate only the owned process. These controls do not cancel a getter and do not establish inspector timeout or isolation behavior.
